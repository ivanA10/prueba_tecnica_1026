# Multi-repo coordination

<!-- updated: multirepo-context-loading 2026-06 -->

Read this file when preflight reports `MULTI_REPO=true` (i.e. `openspec/config.yaml` lists `repos:`) and you are about to plan, dispatch, or verify cross-repo work. Branch ownership defaults to **per-repo PRs with the shared change name** (each repo opens its own `feat/<change-name>` branch). Mode 1 (simple) is **not** typically used cross-repo — for multi-repo work prefer Mode 2 with `--multi-spec-branch <bundle>` per repo.

## Two-tier instruction architecture

| Tier | File | Carries | Budget |
|---|---|---|---|
| Hub (coordination repo) | its `AGENTS.md` | hub-owned sections only: `hub-repo-map`, workflow, memory, boundaries | ≤180 lines |
| Member (each impl repo) | its own `AGENTS.md` | member-owned sections: `project-stack`, `commands`, `repo-pairings` (+ shared) | ≤200 lines |

- The hub's `hub-repo-map` holds ≤3 lines per member (key, path, role, one-line stack), a pointer line ("Full member context lives in `<path>/AGENTS.md` — loaded by the teammate session, never inlined here"), and one `forge:context:<key>:<hash12>` drift line per member.
- Member stack/domain detail NEVER lives in the hub file, in dispatch envelopes, or in briefing cards. Ownership registry: `.forge/section-ownership.json` (shipped at install).
- Generated by bootstrap Modes 6/6b (multi-repo branch of `forge:kickstart`): one audit + 📋 gate per member; `agent-prep` writes each member's sections from inside that repo.
- Existing hubs that absorbed member detail: preflight emits `SECTIONS=needs-split` → re-run Mode 6b; content moves member-by-member under the 📋 gate and is removed from the hub only after the member write is confirmed.

## Loading contract (4 layers — why cwd placement is the rule)

Instruction files only auto-load for the repo a session is **standing in**: Claude Code loads CLAUDE.md/AGENTS.md upward from cwd (sibling repos never load); Codex builds its AGENTS.md chain root→cwd once per session (32KiB cap); OpenCode reads the cwd AGENTS.md and does NOT auto-discover nested or sibling files.

| Layer | Mechanism | CC | OpenCode | Codex |
|---|---|---|---|---|
| 1 | **cwd dispatch** — teammates/subagents for member work ALWAYS start with cwd = member repo root | ✅ | ✅ | ✅ |
| 2 | **Body instruction** — on start, confirm `project-stack` exists in `./AGENTS.md`; missing → `BLOCKED [CONTEXT] missing: project-stack` | ✅ | ✅ (only layer besides cwd) | ✅ |
| 3 | **Preflight check** — hub preflight emits `MEMBER_CONTEXT=` + `CODEX_TRUST=` per member; orchestrator refuses dispatch on `missing` | ✅ | — | ✅ (hooks require project trust) |
| 4 | **CC fast-path (opt-in, default OFF)** — `--cc-add-dir` install flag: `additionalDirectories` from `repos:` + `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` | ✅ only | — | — |

Layer 2 is the only fully portable layer — that's why it is mandatory wording in `rules/agent-common.md`, not advisory. Layer 4 eager-loads N member contexts into the hub session and auto-loads member `.claude/skills/` (CC ≥2.1.32) — duplicate `forge:*` skill names are a known constraint; it is a hub-planning convenience, never a substitute for layers 1–3. Codex subagent inheritance of the AGENTS.md chain is undocumented — dispatch envelopes always restate hard restrictions.

## Coordination repo model

A **coordination repo** owns the spec and `tasks.md`; each implementation repo (`api`, `web`, `mobile`, …) does its work locally. The coordination repo's `openspec/config.yaml`:

```yaml
repos:
  api:
    path: ../forge-api
    role: backend
    branch_prefix: feat/
  web:
    path: ../forge-web
    role: frontend
    branch_prefix: feat/
contracts_dir: openspec/contracts
wave_policy:
  contract_poll_attempts: 10    # default
  contract_poll_interval_s: 30  # default → 5 min ceiling
```

Each repo is its **own** git repo, its own Claude Code/OpenCode/Codex session, and its **own Engram project** (auto-detected from the git remote — see Engram naming below).

## Engram per-project naming

Engram derives the project name automatically:
1. From the git remote URL slug.
2. Override via `ENGRAM_PROJECT=<name>` environment variable (per shell or per workspace in monorepos).

Cross-project queries are explicit — Engram does not blend projects. Use the helper script.

## Cross-project search

`scripts/engram-cross-project.sh` queries each repo's Engram project and aggregates results.

```bash
# Query a topic prefix across the repos defined in openspec/config.yaml
bash scripts/engram-cross-project.sh contract/

# Query a specific subset
bash scripts/engram-cross-project.sh state/wave api web
```

Briefing cards for a member-repo teammate: the hub orchestrator resolves them with `bash scripts/sdd-memory-governor.sh --need <X> --topic-prefix <Y> --repo <key>` — the `--repo` flag routes through cross-project search for that member's Engram project. The ≤1200 mem-token budget is unchanged.

## Topic_key conventions for cross-repo

- `coordination/<change>` — owned by the coordination repo orchestrator. The wave→repo dispatch matrix.
- `contract/<endpoint-slug>` — published by the backend agent **before** the frontend wave starts. Frontend teammates poll for contract topics they depend on.
- `state/wave/<change>/<N>` — upserted per-repo by `agent-sync`. The coordination repo's `agent-sync` aggregates into `state/wave/<change>/aggregate`.
- `handoff/<change>/<from-agent>-to-<to-agent>` — per-repo handoff docs.

All dynamic cross-repo state (wave status, contracts, handoffs) lives in Engram — never in md files. Member `repo-pairings` sections hold slow-changing facts only.

## Wave dispatch sequence

1. Coordinator runs `/sdd` → `forge:propose` → emits coordination plan with `mem_save topic_key=coordination/<change>`.
2. Coordinator dispatches one teammate per implementation repo (parallel), **cwd = that repo's root** (loading-contract layer 1), envelope carrying `repo: <key>` + briefing cards — never member instruction content.
3. Each teammate's first action: confirm `./AGENTS.md` has `project-stack` (layer 2), then `mem_search project:<this-repo>` for prior work.
4. Cross-repo dependencies (e.g., frontend on backend contract):
   - Frontend teammate runs `bash scripts/engram-cross-project.sh contract/ <backend-repo>`.
   - Polls up to `wave_policy.contract_poll_attempts` × `contract_poll_interval_s` (defaults 10 × 30s = 5 min). On exhaustion: return `BLOCKED [CONTRACT] missing: contract/<endpoint-slug>` to the orchestrator (cycle-counter path) — NEVER poll indefinitely.
5. After each wave, `agent-sync` (per repo) upserts `state/wave/<change>/<N>`. Coordinator's `agent-sync` aggregates, and runs `bash scripts/sdd-context-drift.sh --repo <key>` per touched repo — `CONTEXT_DRIFT=<key>` means that member's `project-stack` no longer matches the hub's `forge:context` hash → orchestrator re-renders that member's audit → 📋 re-gate → `agent-prep` refreshes member stack + hub hash.

## Verification gates in multi-repo

Every task in a multi-repo change MUST carry a `Repo:` sub-bullet (planner rejects tasks without it when `MULTI_REPO=true`). The gate executor resolves it before running anything:

```bash
# Repo: api  →  cd "$(yq '.repos.api.path' openspec/config.yaml)" && <gate command>
```

`cmd:` / `playwright:` gates execute **inside the member repo** named by `Repo:` — a hub-run `pnpm test` is always wrong. See `schemas/task-format.md`.

## Setup checklist

- [ ] Create `openspec/config.yaml` in coordination repo with `repos:` map (path + role + branch_prefix per member).
- [ ] Install the harness in the hub with `--repo-role coordination` and in each member with its role (`frontend` / `backend`) — member installs seed the AGENTS.md skeletons that bootstrap fills.
- [ ] Codex users: open each member repo once and accept the trust prompt — untrusted member repos silently drop Forge hooks (preflight reports `CODEX_TRUST=missing(<repos>)`).
- [ ] Run `/sdd` Mode 6/6b on the hub → per-member audits → member context written.
- [ ] Set `ENGRAM_PROJECT=<workspace>` if working in a monorepo (one Engram project per workspace).
- [ ] Confirm `engram serve` is running and reachable at `http://127.0.0.1:7437`.
- [ ] Pick `branch_prefix` (`feature/`, `change/`, etc.) for consistency across repos.

## Monorepos

The same two-tier design applies with nested files instead of sibling repos: root AGENTS.md = hub tier (workspace map, no per-package stack detail); each workspace dir gets its own AGENTS.md/CLAUDE.md (member tier). Claude Code lazy-loads nested CLAUDE.md when files in that subtree are read; Codex picks them up on its root→cwd walk when the session/agent cwd is inside the workspace; OpenCode does NOT auto-discover nested AGENTS.md — the layer-2 body instruction ("Read `<workspace>/AGENTS.md` before working in `<workspace>/`") carries it. Never add root-level `instructions` globs in `opencode.json` that eager-load every workspace file.

- Set `ENGRAM_PROJECT=<package>` per shell when entering that workspace.
- agent-prep emits one `workspace/<pkg>/stack` topic per detected package.
- Teammates entering a workspace `cd packages/api && export ENGRAM_PROJECT=api`.

## Common pitfalls

- **Forgetting `ENGRAM_PROJECT`** in monorepo workspaces — saves leak between packages.
- **Polling indefinitely** for a contract — the `wave_policy` budget is the law: exhaust → `BLOCKED [CONTRACT]`, orchestrator decides.
- **Stale `state/wave/*` topics** — `agent-sync` flags these for soft-delete after `opsx:archive`.
- **Inlining member context into envelopes** — briefing cards stay ≤1200 mem-tokens; member instruction files load via cwd, never via the prompt.
- **Running gates from the hub** — always resolve `Repo:` → `cd` first.
- **Editing the hub repo-map by hand** — it is bootstrap-generated; manual edits break the `forge:context` drift hashes.
